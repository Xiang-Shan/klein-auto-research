4 · The experiment journey

Ten runs, in two phases, on two tracks. Every one of them is a discard or a crash — that was arithmetic, registered in advance (§1) — so the interesting structure is not a frontier climbing but a reach being measured, and one refusal being tested.

§4.1 · The ledger, as the engine draws it

Run order rather than budget, one panel per track. The discards are evidence dots; the crash has no metric and therefore no place on a metric axis, so it sits on the rug where it can still be seen; the sealed cell is a star, outside the adaptive frontier by construction.

§4.2 · E0001 — audit the judge before believing anything

The first cell runs the declared verifier, unchanged, on each of the twelve frozen invalid objects and counts the rejections, then hands the notary the known-valid parabola set as its own artifact — so the acceptance half is performed by the notary's own verifier invocation rather than by the search. Printed: planted: 12, rejected: 12, and a ledger metric of 11, exactly the value the theorem predicts. P3 supported. Nothing after this line would be worth reading if this line had failed.

§4.3 · E0002–E0007 — the same search, two instances, one budget ladder

Three rungs per track — 20000, 200000, 2000000 addability tests — from the development seed block. Because the budget is a strict prefix of one random stream, the three rungs are one trajectory read at three points, so the curve is monotone by construction.

On the 11 × 11 grid: 20, then 21, then 21. On the 31 × 31 grid: 50, then 53, then 54. P2 supported at n = 31 (54 < 62). And at n = 11 —

P1 refuted. The prediction said the search would reach 22 within 2000000 addability tests. It reached 21. The sharper detail is inside the run: the best object was found at evaluation 152572, and the remaining budget — 19014 greedy completions in all — produced nothing better. This was not a budget shortfall.

One number is worth carrying into §5: the same budget bought 19014 completions at n = 11 and 2190 at n = 31, because one completion costs about addability tests. "The same budget" and "the same search effort" are not the same sentence.

§4.4 · E0008 — make the searcher lie, on purpose

One run of the ten was spent making search.py report exactly one point more than the object it wrote. Nothing else changed. The notary refused it:

E0008: crash metric=None
decision_reason: verifier_disagreement: the run reported 21 but the verifier
measured 20 (tolerance 0) — one of them is wrong, and the search is not the
one to ask

The manifest keeps both numbers side by side (reported 21.0, verified 20.0) and results.tsv carries NA: the inflated number reaches no table anywhere in the study. A guard that has never fired is a guard nobody has tested, and the cost of testing it was one phase slot.

§4.5 · E0009, E0010 — the sealed cells, and the surprise

Each track gets one sealed access, rehearsed first with klein run-one --final-test --dry-run (which hands back the development block and prints sealed_dryrun: 1, so the seal survives the rehearsal). The sealed cells then run the same search at the same largest budget from the sealed seed block — one integer different, nothing else.

At n = 31, 55 — a little better than the development lane's 54, still far short. P7 supported.

At n = 11, 22 — the proven maximum, found at evaluation 1612132. P6 supported, and P1's refutation stands beside it, unrewritten.

Same instance, same algorithm, same budget, same commit; the two lanes land on opposite sides of a theorem's ceiling. That pair is the finding, and §5 says what may and may not be concluded from it.

§4.6 · Re-verification

Every development run was re-checked with klein replicate --verify-only: the declared verifier re-run in a fresh process on the pinned artifact, no search, no worktree. Seven records, reproduced: true in every one, tolerance 0.0 taken from verifier.tolerance, difference 0.0 on the primary metric. P4 supported.
