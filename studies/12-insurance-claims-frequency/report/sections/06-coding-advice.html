Model coding advice

Here is the entire per-candidate surface of this study — the actual bytes, included by reference so this page cannot drift from the code that produced the numbers above. Read the four constants under “the candidate” first. That block is an experiment; everything else is machinery that a per-experiment edit is not allowed to touch.




Six things worth stealing



    
  
  • Keep the rung definitions out of the mutable surface. They live in
      lib/rungs.py, which both the entrypoint and the Phase 0 floor
      script import. Re-typing them in the floor script would let the floor describe a
      model the ledger never ran; importing them from the entrypoint would let a
      per-experiment edit silently change what the floor was measured on. A stable library
      has neither failure, and the per-experiment diff shrinks to four lines.
    • 
  
  • Leave the candidate slot empty between experiments.
      CANDIDATE = None and a main that refuses to run without a
      rung. Choosing the rung is the one falsifiable idea a candidate carries, so the
      surface should not silently still hold the last one.
    • 
  
  • Read the bar from the contract; never write it as a literal.
      minimum_delta is loaded from study.yaml inside
      main. Before Phase 0 sets it there is no floor to divide by, so
      the floor-relative keys are simply not printed — and a prediction whose key is
      missing is inconclusive, not refuted, which is the honest answer.
    • 
  
  • Route every partition through load_partition. It reads
      the contract alone and prints the split_fingerprint: line the notary
      compares against the one the data gate froze, so a partition that silently changed
      is a crash by design. The only integer seed in this study's code is a
      fit seed, and it reaches nothing but two estimator constructors.
    • 
  
  • Print the comparison; do not reconstruct it. Every run refits its
      named reference rung on the same rows, in the same process, and prints
      delta_vs_reference, delta_in_floors and
      brier_delta_vs_reference. A paired comparison assembled later by
      subtracting two log files is not paired; it is two numbers that happen to be near
      each other.
    • 
  
  • Ship an instrument with every accepted risk. The three
      twin_free_* keys are four lines of entrypoint. They are the difference
      between “we accepted a known leakage risk” and “the accepted risk
      is worth at most 0.001415 of AUC per rung, and here is the number on every run,
      including the sealed one”.
    • 




Pitfalls this study actually hit



    
  
  • A floor is a property of the pair, not of the data. Measure the
      floor of the comparison you are going to make, and if you declare one global bar on
      a ladder that spans model classes, say so and publish the pair-specific numbers
      beside it.
    • 
  
  • The order statistic in the bar rule grows with the replicate count.
       is a guard against
      underestimating  from few replicates; at a thousand
      replicates it inflates the bar for a reason that is arithmetic, not measurement.
      Choose the replicate count deliberately, write the choice down first, and report
      what the other choice would have given.
    • 
  
  • A claims lock is not a draft. A number's home may never change, and
      a claim's sentence may never change. Home magnitudes where magnitudes live, and keep
      identifiers containing digits out of claim sentences — the scanner reads the
      digit in log1p as a number nobody measured.
