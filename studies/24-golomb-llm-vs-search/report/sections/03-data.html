There is no dataset, only an instance and an oracle

The modality is none: no rows, no columns, no train and test split. What the study reads is one tiny prepared file, data/prepared/instance.json, produced by the deterministic prepare.py and hashed at the DATA gate. It declares the two lanes (development orders 8–11, sealed orders 12–13), three trials per order, a budget of 2000 candidate evaluations, a batch size of 10 for the LLM arm, and the seed blocks. The “split” is the pair of lanes. The DATA gate therefore ran a verifier card in place of a leakage audit, and its call was go, with cautions (the gate record, not this page, holds the status).

The value-pattern check, applied to an object with no columns

The rule is never to trust a type, so every scalar in instance.json was inspected by value. All counts and lengths are JSON integers: no numbers stored as strings, no booleans, no sentinels such as -1 or NA. The optima keys are strings of integers that search.py converts with int(). One convention to know: order 1 has length 0 by convention, and no lane uses it.

Where the answer key comes from, said honestly

The lengths compared against are OEIS A003022 values for orders 8–13 (ref:oeis_a003022). They are pinned inside the verifier (ORACLE), and the verifier refuses an instance.json that disagrees with any pinned field, because the file sits where the mutable search.py has just run with write access. Who established that nothing shorter exists is a literature fact this study did not re-run: the data card records that the OEIS entry gives no per-term reference for these orders, links Shearer's tables, and credits distributed.net only for far larger orders. So “tabulated optimum” means “the OEIS value, from exhaustive searches by others”. What the DATA gate did check independently is attainability: tabulated rulers transcribed by hand for orders 8–13 were accepted by the verifier with exactly the table lengths.

The gotchas that shaped the study

  1. The sealed orders are public. “Sealed” protects against adaptive tuning of search.py (one run per arm, a mandatory dry run first). It does not make the sealed orders unseen by the model. A sealed LLM match would have been consistent with recall, which is why the study registers the first-batch signature beside the sealed prediction.
  2. Two holes found by an adversarial review, then closed. The artifact named its own lane, so a development run could have submitted a sealed-lane artifact; and the optima lived in a file the searcher could rewrite. The verifier now maps the notary's evaluation kind to the lane and carries the pinned oracle.
  3. Budget parity is self-reported. The verifier enforces that each pair spent exactly the budget, but the counter lives in the mutable file. The independent record for the LLM arm is the call ledger.
  4. The budget is matched in verifier calls, not in information or time. The annealer sees one verdict per candidate; the LLM sees one text block per 10. Every comparison is phrased “at a matched number of candidate evaluations”.
  5. No lane field is a partition. With split.kind: none there is no row split to fingerprint; the lane is guarded by the verifier's evaluation-kind check and its pinned oracle instead, and the engine's split-fingerprint check is advisory for this study.

Controls on the verifier

Before any lane run, the verifier was exercised with hand-made artifacts in a scratch directory. It rejected planted invalid rulers, forged lengths, wrong-lane artifacts and a tampered oracle, and it accepted the hand-transcribed tabulated rulers, scoring 12 of 12 on the development lane and 6 of 6 on the sealed lane. A script in sweeps/ re-runs nine of those refusals against the final verifier. Two caveats the referee asked this page to carry: the data card labels these controls the other way round from the conventional usage in findings (the gate-hashed card is left as written), and the scratch artifacts are not pinned, so their record is the card's text. These controls test the verifier. They say nothing about either arm.
