One mechanical note that matters for reading the smokes below: `klein verify`
on a schema-3 study self-commits `verify_receipt.json` unless `--no-receipt`
is passed (AGENTS.md's own "state files are receipts" doctrine — experiment
loop contract, layer 3). When it runs, the printed summary carries one more
line than the receipt's own `summary.checks` field — the "receipt written"
check is bookkeeping added after the fact and, by construction, cannot
describe itself (`kleinlib/checks.py`'s own docstring says so). Neither driver
was told about `--no-receipt`; AGENTS.md's run-commands section never
mentions it either, so a driver following doctrine literally will legitimately
write and commit a receipt. That is Klein working as designed, not a driver
defect — see how each smoke below handled it.

### 3. Copilot CLI — live smoke BLOCKED, notarized-fallback recovery (2026-09-03, this audit)

- Version: GitHub Copilot CLI 1.0.82; session model `claude-opus-5`, effort
  `max`; Copilot-subscription auth. Entry path under test: **auto-read
  `.github/copilot-instructions.md`**, which designates `AGENTS.md` canonical
  (file confirmed present and correctly pointing there — see Findings below
  for why its content is nonetheless a problem).
- Command — the identical invocation shape that sufficed in the v1.0 audit:

  ```bash
  copilot -p "<task prompt>" --allow-tool 'shell(uv run*)'
  ```

- Result: **did not execute the verification itself.** It correctly *derived*
  the doctrine command — `uv run --locked klein verify --study
  studies/10-hubble-1929-replication`, byte for byte — but every attempt to
  *run* any `uv`/`klein`/`python` invocation was denied, seven times: three
  variants of that command (bare, and twice piped/chained with `cd`), a bare
  `uv --version`, a direct `.venv/bin/klein --help`, an absolute-path `uv
  --version`, and a `uv run --no-sync klein verify ...` retry — all returning
  "Permission denied and could not request permission from user," despite the
  `--allow-tool 'shell(uv run*)'` grant that sufficed for the identical
  pattern in the v1.0 audit. The block was not confined to `uv`/`python`
  either: a delegated `Task(claude-opus-5)` subagent's own two attempts
  (chained `git log`/`grep` ancestry checks) and two more top-level chained
  `git merge-base --is-ancestor ... && ... || ...` checks were **also**
  denied — eleven denials across the session in total. A separate set of
  simple, single-clause commands (`ls`, `git status`, `git branch`, `cat`,
  `grep`, `echo`, plain `git log`) ran normally throughout, so the block
  correlates with either the binary (`uv`/`python`) or with multi-clause
  `&&`/`||` command structure — not cleanly with "these three binaries only,"
  which was Copilot's own self-diagnosis.
- Root cause, independently confirmed by reading Copilot's own local config:
  its trust store lists an older, differently-pathed local clone of this
  repository as trusted, but **not** this worktree and **not** the repo's
  current path either — this specific working directory has never been
  interactively trusted by this Copilot CLI installation, and `--allow-tool`
  did not substitute for that trust gate this time. A per-directory trust gate
  plausibly explains the chained-command denials too, if it falls back to
  stricter, harder-to-statically-verify-as-safe handling for multi-clause
  commands in an untrusted directory. Copilot's own self-diagnosis mid-session
  ("the environment declares only `git, curl, gh`") could not be
  independently confirmed from the config
  files read during the session; it is reported here as Copilot's stated
  belief, not a verified mechanism.
- Recovery: rather than fabricate a result or claim it had run the check,
  Copilot located the study's own **already-committed** `verify_receipt.json`,
  confirmed via `git log`/`git merge-base --is-ancestor` that its commit
  (`0310ad2 klein: verify receipt (39 checks, 0 failed)`, written during study
  10's own development on 2026-09-03) is a genuine ancestor of the audited
  HEAD — not fabricated, not stale relative to any change in this tree — and
  read it directly. It reported: **39 checks, 0 failed** (matches ground
  truth), phase `confirmation` (cross-checked against `study_state.json`'s
  `status`/`label` fields — also matches), and a clean tree (also matches).
  It undercounted the warnings, however: it reported **3** `[WARN]` checks by
  its own grep (`contract-driven split`, `analyze.py`, `tutorial numbers`),
  where the receipt actually carries **5** (it missed `prepared-data
  fingerprint` and `figure re-render`). It disclosed the whole situation
  plainly rather than hiding it: *"I did not work around it (no bare python,
  no .venv/bin/klein)."*
- All headline numbers match ground truth and nothing was fabricated, but
  this **does not meet the live-smoke success bar as defined** — the driver
  must execute the verification itself, and this run read a pre-existing
  artifact instead. `git status --porcelain` was empty throughout (Copilot
  made no commits and no edits — its own footer read "Changes +0 -0"); wall
  time ~8m02s end-to-end (its own footer separately reports "AI Credits
  203.33 (6m 37s)" of compute, plus ~1.5M tokens up / 26.6k down — an order of
  magnitude more than Codex's run, driven by the repeated denials, config-file
  reads, and the delegated subagent attempt). Exit: process returned a normal
  structured final report, not a crash trace (explicit `$?` not separately
  captured, same caveat as the Codex row).
- **Verdict: FAIL against the stated success bar, with an honest and accurate
  fallback.** Scored as a genuine regression from the v1.0 outcome (15 checks,
  0 failed, live-executed, exit 0, 4m22s) using the identical flag, in this
  environment — see Findings below for the likely fix.

## Findings for AGENTS.md

1. **`.github/copilot-instructions.md` has drifted behind Klein 2.0 and should
   be updated or trimmed.** It still describes the pre-2.0 "six-stage
   lifecycle," lists gates as only `consult|data|method` (no mention of Gate
   3 / REFEREE), says the mutable surface is unconditionally `train.py`
   (2.0's is `entrypoint.mutable`, `train.py` only by default for `predict`),
   and never mentions `klein doctor`, `predict`, `claims`, `replicate`,
   `sweep register`, `headroom`, or `stop`. It correctly points at `AGENTS.md`
   as canonical, so no driver was factually misled by it in this audit, but a
   Copilot user who reads it for specifics (as its own "details in AGENTS.md"
   framing invites) would get a stale picture of the gate and CLI surface.
   Recommended fix: mirror `CLAUDE.md`'s own pattern — state the golden rules
   that won't drift (locked `uv run`, never hand-edit ledgers, studies run on
   `experiments/<study>` branches) and delegate stage-by-stage specifics to
   `AGENTS.md` by reference instead of restating them, so it can't drift again.
2. **No `AGENTS.md` sentence needs correcting.** Every doctrine claim checked
   this cycle — Codex and Copilot auto-reading their respective entry files,
   the Gemini CLI / Qwen Code `context.fileName` mechanism, GLM & other
   Anthropic-compatible CLIs inheriting `CLAUDE.md` via the real Claude Code
   binary, Claude Science's sandboxed shell/code execution and same-model
   reviewer, llama.cpp's native Anthropic Messages API, and the wider
   `AGENTS.md` ecosystem listing — verified accurate against current official
   sources. The one real regression found (Copilot CLI row 3) is a local
   trust-store / operational issue in this Copilot CLI installation, not a
   false claim in Klein's own documentation — worth flagging to anyone running
   Copilot CLI non-interactively for the first time in a fresh clone or CI
   worktree (trust the directory, or find its non-interactive trust-bypass
   flag, before `--allow-tool` grants can take effect), but not an `AGENTS.md`
   text change.
